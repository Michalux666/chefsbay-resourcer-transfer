# Parity: integration rehearsal (WP10) - all nine packages together, on Linux, fakes only

Owner: the end-to-end rehearsal engineer. Legacy source: nothing is read from the legacy system here; the point is the seams between the new packages. Everything below was run in a Linux copy of the repo (Ubuntu 24.04, Node 22.22.1, Python 3.12) with `bash tests/e2e-linux.sh`.

## 1. How to run it

```
bash tests/e2e-linux.sh                 all scenarios, then a summary (about 18 minutes; the last full run of 2026-09-29 took 934 s and 12 of 12 passed; scenario 13 was added 2026-09-30)
bash tests/e2e-linux.sh --only 02,05    some scenarios
bash tests/e2e-linux.sh --unit          also the whole unit suite: node --test "tests/**/*.test.js"
bash tests/e2e-linux.sh --keep          keep the per-scenario profiles under $E2E_ROOT/worlds
```

The script copies a repo that sits on a Windows drive mount to a Linux directory, runs `npm install` in `resourcer/` (cached), creates a python venv with fastapi and httpx when `E2E_PYTHON` is not given, and runs `tests/e2e/NN-*.e2e.js` one file at a time (`.e2e.js`, so the unit glob `tests/**/*.test.js` does not pick them up). The header comment of the script is the reference. Exit code = number of failed scenarios.

Unit suite: 1614 tests, 1610 pass, 0 fail, 4 skipped (the real-Chromium Reed tests; set `REED_REAL_CHROMIUM=<binary>` on a machine that has one). Run bare from the repository root, `node --test "tests/**/*.test.js"` silently skips 36 more tests (backup, maintenance vacuum, the real Phase 2, two wrappers, the python plugin suites) because `better-sqlite3` lives in `resourcer/node_modules` and is not resolvable from `tests/`, and no python with fastapi is found. `--unit` sets `NODE_PATH` and `RESOURCER_PYTHON` so nothing skips; do the same by hand (`NODE_PATH=$PWD/resourcer/node_modules RESOURCER_PYTHON=<venv>/bin/python node --test ...`) before trusting a green run.

## 5. Not fixed (observations for the owner)

1. **Two browsers in a `both` run.** Phase 2 downloads the Caterer CVs through the warm Caterer browser while the Reed browser is up. The phase 1 scrape and unlocks end before Reed starts (asserted). RAM: about one extra Chromium for a few minutes.
2. **Create-then-kill window.** A Phase 2 killed between the Zoho create and the attach is recovered by pushing again; Zoho answers DUPLICATE and the duplicate path removes the CV, so that one candidate has no CV. At-least-once semantics; the window is one attach latency per candidate.
3. **Killed leaf tools.** A killed browser call or screening child is a per-candidate or per-page error by design (an unlock is never re-sent). A killed screening child is read as a reviewer parse failure: the run ends without a halt and Phase 2 consumes the territory, on purpose (keeping it would re-run a deterministic failure every minute).
4. **Session death in the middle of a run** (after the runner check and phase 1's own validation) is not detected by phase 1: pages fail, five in a row stop the run, the territory is consumed (legacy behaviour). The next run signs in again.
5. **Halt / retry loop.** If the health canary passes but the real reviewer call keeps failing, the halt clears and re-raises once per cycle (about a minute apart); nothing is lost (the territory is kept) and the alerts are deduped, but there is no counter that stops it.
6. **Shadow log.** `shadow/screening-*.jsonl` keeps the redacted snippet text for 180 days (D3). Names, e-mails, phones and postcodes are not in it (tested); "no snippet text on disk" is only true after 180 days, or with `shadow.storeText: false`.
7. For the docs package: `docs/ENV.md` needs the variables above plus `RESOURCER_TEST_NOW`; INSTALL must run `migrate-schema.js` then `backfill-run-results.js --strict` (now exit 0) then `preflight-db.js`; OPERATIONS needs the alert keys `db-unfit`, `stranded-recovered`, `stranded-unrecoverable`, and the recovery commands `pipeline-watchdog.js --clear-cooldown` (now resumes at once), `caterer-login.js --open-link`, `backup-db.js --restore`.
