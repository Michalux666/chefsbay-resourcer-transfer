## Fixes and deliberate changes (all reversible by config)

R1. **Chrome 153 token capture.** `Network.setRequestInterception` and `Network.requestIntercepted` are not used anywhere (a hygiene test greps for them). The Bearer is taken from `Network.requestWillBeSent`, `Network.requestWillBeSentExtraInfo` (URL remembered per requestId, header names matched case-insensitively) or `Network.responseReceived.response.requestHeaders`, only for `api.reed.co.uk`, only when the token is at least 50 characters. Verified against the fake CDP that rejects unknown methods with `-32601`, and against a real Chromium 145 (see "Verification").
R2. **Credentials** only from `secrets/reed-credentials.json`. Values are embedded into page scripts with `JSON.stringify`, set through the native value setter followed by `input` and `change` events (works for plain and state-driven forms), never printed or logged, and the legacy `localStorage` dump to stderr (which could contain a token) is gone. Missing or placeholder values exit 3 before any browser work. The file mode is checked (warning if group/other readable).
R3. **Login flow** polls instead of fixed sleeps (ceilings: form 15 s, password step 10 s, Turnstile 15 s, redirect 12 s, capture 20 s; the legacy waits were 5 s + 1 s + 10 s + 8 s), supports an identifier-first (two step) form, and treats an already-logged-in profile (redirected away from the login page) as success. Selectors are the legacy ones plus `name=username`, `id=username`, `autocomplete=username`. Total worst case is about 75 s, so `reed-phase1.js` gives the login a 90 s kill timeout instead of 60 s (`REED_LOGIN_TIMEOUT_MS`).
R4. **No token on stdout.** `cdp-reed-full-login.js` saved the session AND printed `TOKEN:<jwt>`, which `reed-phase1.js` parsed. It now prints `REED_LOGIN_OK expires=<iso> ip=<claim>` (the `ip` claim is a public IP, useful to diagnose 451) and `reed-phase1.js` checks the saved session instead.
R5. **Human-assisted first login and the Turnstile block.** When the login page shows a Cloudflare Turnstile / interstitial that does not resolve (before the form, at the email step, before submit, or after submit) the script raises ONE `critical` alert (`key: 'reed-human-login'`, once per episode, R21) whose text carries the exact command `cd <RESOURCER_HOME> && node scripts/cdp-reed-full-login.js --human`, writes `runtime/reed-login-block.json`, prints `REED_LOGIN_BLOCKED_TURNSTILE`, sets `reed-status.json` to `auth_failed` and exits 1. It never retries and never loops: while the block file is younger than `REED_LOGIN_BLOCK_HOURS` (12) further automatic attempts exit 1 immediately without touching the browser and without a second alert; when the window has passed one automatic attempt is made again and, if Turnstile is still there, the block is re-recorded WITHOUT a new alert. `--ignore-block` forces an attempt. `reed-phase1.js` then writes the auth marker with reason `turnstile_blocked` and exits 1 (`REED_AUTH_FAILED`). While the block (or the marker, or a running `--human` session) is fresh, `run-pipeline.js` does not start Reed at all (R20), so the pending searches keep their bounded Reed retries; only the single run that probes after the window can still turn into a placeholder Reed queue with `authFailed: true`.
R6. **Launcher** (container hardening in R27). `ensure-chrome-cdp.js` uses `CHROMIUM_PATH` (else `/usr/bin/chromium`, `chromium-browser`, the Hermes image path file, `google-chrome`, `google-chrome-stable`), `spawn('xvfb-run', ['-a','-s','-screen 0 1920x1080x24', chromium, ...flags], {detached})` with stdout/stderr redirected to `logs/reed-chrome.log` (so no pipe of the caller is inherited), profile `state/chrome-reed` (0700), port `REED_CDP_PORT` (9222). Flags: `--remote-debugging-port --remote-debugging-address=127.0.0.1 --user-data-dir --no-first-run --no-default-browser-check --restore-last-session --disable-background-timer-throttling --disable-backgrounding-occluded-windows --no-sandbox --disable-dev-shm-usage --password-store=basic --disk-cache-size=104857600 --window-size=1920,1080 <target url>` (legacy set minus the Windows-only occlusion flag, plus the container flags, a stable cookie-encryption store and a cache cap). It verifies readiness by `GET /json/version` (logs the browser version), reuses a live instance, replaces a stale non-serving instance, removes stale `Singleton*` files, serialises concurrent launchers with a launch mutex, fails fast when the browser exits during startup and tears the tree down on a readiness timeout. A CDP endpoint on the port that belongs to no process of the Reed profile is NOT adopted (`CDP_LAUNCH_FAILED ... not the Reed profile`; `REED_CDP_TRUST_EXISTING=1` disables the check).
R7. **Shutdown (found by test against a real Chromium).** Plain SIGTERM loses the login: the cookie database is not flushed and a relaunched browser is logged out. `--stop`, `--restart`, `reed-phase1.js` and `run-pipeline.js` therefore quit the browser with CDP `Browser.close` first (cookies and session state are flushed; both session and persistent cookies survived a restart in the real-browser test), wait up to `REED_CDP_CLOSE_WAIT_MS` (10 s), and only then run the forced tree shutdown: SIGTERM to the browser process alone (8 s), then SIGTERM to the rest, then SIGKILL, then the wrapper, then Xvfb, then `kill(-pgid)`. `xvfb-run` removes its own Xvfb when chromium exits, so no Xvfb is orphaned (asserted by parentage in the Linux tests). Caches that are safe to drop (`Default/Cache`, `Code Cache`, `GPUCache`, shader caches, service-worker caches) are removed after a stop; cookies and local storage are kept. Processes are found through `/proc` (no `ps`), matched on the joined command line because Chromium rewrites its process title so `/proc/<pid>/cmdline` is ONE element (found by the browser-caterer package and confirmed here with a real build); the caller and its ancestors are never signalled.
R8. **Browser lock** (`runtime/browser.lock`), the only piece shared with the Caterer side. Format `{owner: 'caterer'|'reed', pid, startedAt, purpose}`, created with `O_EXCL`. A holder is stale when its pid is dead, or it is older than 4 h. `require('./ensure-chrome-cdp').browserLock` exports `acquire(owner,{purpose})` -> `{acquired, borrowed, reentrant, holder, release}`, `wait(owner,{waitMs,pollMs})`, `release`, `read`, `state`, `reedMayUse`. A lock held by an ANCESTOR process (or the pid named in `RESOURCER_BROWSER_LOCK_HOLDER_PID`) is BORROWED: this is the hand-off from `phase1.js` to `run-pipeline.js`, and release is then a no-op. The Reed browser never launches, is never reused and is never stopped while a live non-Reed holder that is not an ancestor exists (`CDP_LOCKED`, exit 4). `run-pipeline.js` waits up to `REED_LOCK_WAIT_SEC` (300) for the lock, then records `authFailed` with reason `browser_lock_busy` (so Phase 2 keeps the pending search for retry) and still runs Phase 2 once.
R9. **Reed browser lifecycle.** Whoever ACQUIRED (did not borrow) the lock stops the browser when it is finished: `run-pipeline.js` after Phase 2 (Phase 2 downloads Reed CVs through the same tab), standalone `reed-phase1.js` at exit. The order is browser quit first, lock release second. `REED_KEEP_CHROME=1` skips the stop (operator debugging). A browser left behind by a killed run is reused by the next Reed run, or reaped by `node scripts/ensure-chrome-cdp.js --stop-if-idle` (safe for a supervisor tick: it does nothing while any live lock holder exists).
R10. **D4: Reed no longer burns candidates when screening is down (the legacy rule that a screening outage must not consume candidates, extended 2026-09-29 by the port: ANY screening attempt that is not a successful parse is Unavailable; the extension is a design default, not yet confirmed by the owner, DECISIONS OD1).** `runAiScreening` returns per-candidate results flagged `unavailable: true` (with a short data-free `failure` such as `exit 1`, `timeout`, `killed by SIGKILL`, `unparseable output`, `results missing for 1 of 25 candidates`) when the screening CLI answers exit 3 or prints `API_UNAVAILABLE` (stdout prefix or stderr token), exits 1 or any other non-zero code, is killed by the 15 minute timeout (`REED_SCREEN_TIMEOUT_MS`) or a signal, cannot be spawned, when the screening script is missing, or when exit 0 is followed by output that is not a successful parse. A successful parse is a JSON array whose entries are objects with an `id` and a boolean `approved` and that covers EVERY candidate sent (contract: one element per input); an empty array, a non-array, a `null` entry, a string `approved` or a missing candidate is Unavailable. The page loop then marks NOTHING seen or rejected, does not count the page (`pagesScraped`, `inDb`, `crossDedup`, `noPermit` are applied only when a page is settled), waits `SCREEN_PAGE_RETRY_PAUSE_SEC` (120) and retries the SAME page. The failure counter resets on any successful screening. The third consecutive failure raises `lib/pipeline-halt.setHalt('AI screening unavailable', ..., {remedy, blockedRun:true})` naming the last failure kind in its detail (the halt library alerts once), sets `errors: 1` and `screeningHalted: true` in `phase1Stats`, stops paging, writes the queue with what was screened so far and exits 0 (`REED_SCREENING_HALT: pipeline halt raised`). A run that STARTS while the pipeline is already halted does no browser work at all, writes an empty queue flagged `screeningHalted` and exits 0; a halt raised by someone else mid-run stops paging the same way. `--skip-screening` ignores the halt. Nothing is fail-closed any more: the legacy `screeningModel: 'error'` path (exit 1 / unparseable output rejected and marked the whole page) is gone. Trade-off: a screening CLI that is deterministically broken for Reed input now halts the shared pipeline after three attempts instead of silently rejecting pages; the watchdog's screening probe clears such a halt when the gateway itself is healthy, so a broken CLI would re-halt on the next Reed run (no candidate is lost either way).
R11. **No snippet or CV on disk.** The screening CLI is called as `node ai-review.js --mode batch ... --candidates-file -` with the JSON on stdin (the legacy `.reed-phase1-batch-*.json` and `.reed-anon-cvs/` files are gone; a test walks the whole home for the CV text). CV files written by Phase 2 (`cv-reed-<id>.<ext>`) and `candidate-*.json` stay the lifecycle package's business; `reed-download.js` writes them 0600.
R12. **PII out of logs.** Candidate names are not printed (legacy printed `[id] name` on every skip/approve/reject line), and the profile's e-mail/phone are not logged. Error text never includes CDP command parameters (legacy timeouts echoed the first 50 characters of the parameters, which for token seeding carried part of the JWT).
R13. **Status for the dashboard.** `runtime/reed-status.json` is exactly `{state, updatedAt, detail}` (`state` one of `ok|auth_failed|disabled`, `updatedAt` an ISO string with milliseconds and `Z`, `detail` always a string of at most 200 characters, secrets redacted); `writeReedStatus` refuses any other state. It is written `ok` after a successful pre-flight, login or refresh (the same call also lifts a recorded login block and marker, R20), `auth_failed` (detail = reason) on every auth failure, human-login block and missing credentials, and `disabled` (detail `RESOURCER_SOURCES=<value>`) by `run-pipeline.js` on EVERY start while `RESOURCER_SOURCES` excludes Reed, including caterer-only runs; enabling Reed again removes a stale `disabled`. A lock conflict does not change it. `runtime/reed-auth-failed.marker` keeps `{reason, failedAt (ISO)}` plus the legacy `jobTitle` and `location`. Both files were read back through the real `plugin_api.reed_state` (FastAPI venv in WSL): `disabled`, `ok`, `auth_failed` from the status file, the marker winning when newer, and `ok` again after a completed login, all as intended. Nothing in the pipeline calls run-pipeline in a caterer-only run, so the supervision tick or the pre-flight should run `node scripts/reed-api-client.js --sync-status` (see Requirements).
R14. **HTTP 451** on the first search page (JWT `ip` claim from a non-UK SSO session) exits 1, writes the marker `reed_451_international`, sets `auth_failed` and raises one critical alert naming `cdp-reed-full-login.js --clean`. Later pages: 451 stops paging.
R15. **Browser relaunch.** `reed-browser-fetch.js` makes ONE launcher attempt per process when the CDP endpoint is unreachable or has no Reed tab (browser killed by the OOM killer mid-run); `REED_AUTO_RELAUNCH=0` disables it.
R16. **Tab choice** is deterministic and shared by the refresh and the API proxy (`pickReedTab`): a tab already on `candidates/search` first, then any `reed.co.uk/recruiter` tab, then any `reed.co.uk` page (the refresh alone falls back to the first page). Legacy picked the first recruiter tab in both places, which could differ from the tab the refresh navigated. `reed-refresh-token.js` also treats any `reed.co.uk` page (including `secure-recruiter`) as a usable Reed tab and lets the navigation decide.
R17. **`RESOURCER_SOURCES` gate** (`caterer` default, `reed`, `both`) in `run-pipeline.js`. When it excludes Reed the Reed step and its browser are skipped, no placeholder or merge is written, and Phase 2 runs ONCE on the Caterer queue (whose own `sources` field keeps the pending-search safety net of Phase 2 from looping). Any other value is treated as `caterer` with a warning. `watchdog-runner.js` already gates the requested sources at run start; this is the second line.
R18. **`run-pipeline.js` housekeeping.** Child output is echoed to stderr as `[reed] ...`, `[phase2] ...`, `[optimiser] ...` (the legacy captured it in memory, so a Reed failure was undiagnosable unless it failed); `updateMemory` (edited an OpenClaw `MEMORY.md`) is removed; the `PERFORMANCE` line is ASCII; the run-lock file is created exclusively; JSON writes are atomic; children run under `paths.NODE`.
R19. **Cosmetic:** ASCII-only output (`+`, `x`, `->` for the legacy check/cross/arrow glyphs), `--help` on every CLI, `main` functions return exit codes and only the CLI wrapper calls `process.exit`, CDP command timers are cleared, `pdf-parse` parsers are destroyed.

R20. **Reed hold: a pending human login does not spend Reed retries (2026-09-29).** Before it starts the Reed step (and before waiting for the browser lock) `run-pipeline.js` asks `reed-api-client.authHold()`. Reed is on hold when (a) a `--human` session is running (`runtime/browser.lock` held by a live `reed` process with `purpose: human-login`, so the pipeline does not wait `REED_LOCK_WAIT_SEC` and then record `browser_lock_busy`), (b) `runtime/reed-login-block.json` is younger than `REED_LOGIN_BLOCK_HOURS` (12), or (c) `runtime/reed-auth-failed.marker` is fresh: for `turnstile_blocked` and `reed_451_international` (people needed) the same 12 h window, for every other reason (`auto_login_failed`, `post_login_verify_failed`, `reed_credentials_missing`, unknown or unreadable marker; unreadable or dateless markers are judged by file time) `REED_AUTH_HOLD_MIN` minutes (30; 0 switches the short hold off). `browser_lock_busy` never holds. On a hold the Reed step is skipped and logged as `REED_HELD: <reason> (<detail>)`; no Reed child, no browser, no placeholder and no `authFailed` flag; Phase 2 runs ONCE on the untouched Caterer queue (whose `sources` field is `both`, so the real `process-approved-queue.js` completes the territory and deletes the pending search as "pipeline complete" without touching `reedAuthRetries`; proven with the real Phase 2 in `tests/reed/hold-phase2.test.js`, next to the contrast case where a genuine Reed auth failure keeps the file and counts a retry). Cost: the Reed half of a territory processed during a hold is skipped for that cycle (same as `RESOURCER_SOURCES=caterer`); the scheduler picks the territory up again at its next interval. A hold ends by itself when its window passes (the first run after that probes Reed once) and immediately on success: a completed login (`finish`), a successful token refresh (`markAuthOk`, which lifts the block and every marker except `reed_451_international`, which only a completed login lifts) or a phase 1 pre-flight that authenticates. `reed-refresh-token.js` refuses to touch the browser while a `--human` session runs (`REED_RELOGIN_NEEDED`, exit 1, no CDP traffic), so the daily pre-flight cannot navigate the tab the operator is logging in to. `node scripts/reed-api-client.js --auth-state` prints the decision.

R21. **One alert per episode.** `alertOnce(key, alert)` (in `reed-api-client.js`, state in `runtime/reed-alert-episodes.json`) raises the first alert of a key and stays silent until `clearAlertEpisode(key)` closes the episode; a forgotten episode is reminded after `REED_ALERT_REMIND_HOURS` (72; 0 = never). Keys: `reed-human-login` (critical, exact `--human` command and the ssh/inspect steps; closed by a completed login or any successful auth), `reed-credentials` (critical, schema of `secrets/reed-credentials.json` and the `--check-credentials` command; closed by a valid file, which also lifts its marker), `reed-451` (critical, the `--clean` recovery command; closed when a run gets past the first search page). Alert texts use plain `USER@INSTANCE_HOST` placeholders (no angle brackets, which some chat channels swallow). Before this, a block that recurred after the 12 h retry window, `--ignore-block` retries, missing credentials (no alert at all) and every HTTP 451 run each produced their own alert.

R22. **Anonymized CV file names.** `downloadAnonymizedCv` writes `cv-reed-<id>.anon<ext>` (`ext` one of pdf, docx, doc, rtf, txt, else pdf; e.g. `cv-reed-9007.anonpdf`), replacing `cv-reed-anon-<id>.<ext>`. `lib/cv-retention.js` (`classifyDownloadName` rule `^cv-(reed-)?(\d+)\.[A-Za-z0-9]{1,10}$`) now classifies it as a CV of source `reed`, so the orphan sweep removes it after `orphanDays` (14); `findExistingCv()` and `cvBasenames()` only look for the five real extensions, so a redacted CV can never be picked up as the paid CV and attached to a Zoho record. Candidate ids that are not numeric are refused (`candidateId must be numeric`) before any request, credit or file, in `downloadCandidate`, `downloadCv` and `downloadAnonymizedCv`. Nothing in the pipeline calls the anonymized download to disk (phase 1 extracts text from memory), only the CLI `--anonymized-cv`.

R23. **Launcher process matching pinned.** `ensure-chrome-cdp.js` matches the Reed profile on the space-joined command line (`cmdOf`, `hasFlag`, `profileProcs` exported): real Chromium rewrites `/proc/<pid>/cmdline` into one element, ordinary processes have one element per argument. The match is on the whole argument, so a look-alike profile (`chrome-reed-caterer`) is never stopped. `--stop`, `--stop-if-idle` and `--restart` are tested against a process whose title is one joined element (Linux) and against records of both shapes (everywhere).

R24. **Approvals are marked seen only after the queue exists (review round 2026-09-30, phase2-reed 16, HIGH).** `reed-phase1.js` used to call `seenReedCandidate` for every screened candidate inside the page loop while the only durable record of an approval, `reed-approved-queue-<runId>.json`, was written once after the loop: a kill after page 1 (70 minute ceiling, cron timeout, restart, OOM) left every approved candidate marked seen, in no queue, skipped by every later run. Now a rejection is marked at once (a final decision), an approval is remembered in memory (`approvedIds`, which also stops the same candidate on two pages being screened twice) and `markApprovedSeen` marks the approvals only after `writeApprovedQueue` has written the file (atomic rename, mode 0600) and the file has been read back with every approved id in it. A write or read-back failure throws (exit 1, `FATAL`) with the approvals unmarked, so the next run screens them again (LLM tokens, no Reed credits). Stdout gains `[Reed Phase 1] approvals recorded as seen: <n>`. Tests: `approval-mark.test.js` (an unwritable `downloads/` leaves only the rejections marked and the re-run queues all approvals; a normal run's marked set equals queue plus rejections; the same candidate on two pages once; SIGKILL of the real process between page 1 and the queue write, then a re-run picks up all 29 approvals) fail on the previous code and pass now. `process-approved-queue.js` still writes the Zoho id with `UPDATE ... WHERE reed_id = ?`, which needs the row this step creates; that is why the mark is kept after the queue write instead of being removed. What remains: a kill AFTER the queue file exists (Phase 2 or `run-pipeline.js` dying) leaves marked candidates and an orphan queue that nothing consumes (`recover-stranded-phase1.js` only knows Caterer queues). Full fix, owned by other files: `process-approved-queue.js` upserts the Reed row when it processes the candidate (`INSERT INTO candidates (reed_id, source, unlocked, zoho_id) VALUES (?, 'reed', 0, ?) ON CONFLICT(reed_id) DO UPDATE SET zoho_id = excluded.zoho_id`), after which `markApprovedSeen` can be dropped (it stays correct either way), and `recover-stranded-phase1.js` recovers through the merged queue.
R25. **Daily profile-view budget (phase2-reed 27).** After the login succeeds `reed-phase1.js` reads `reed_daily_usage` (through `reed-download.getTodayUsageFromDb`): with no view left it screens nothing, marks nothing and writes an empty queue flagged `dailyLimitReached` (`REED_DAILY_LIMIT: ...`, `REED_PHASE1_SUMMARY` printed, exit 0); with fewer views left than `--cv-limit` the limit is lowered to what is left. An unreadable table changes nothing. Before, the run screened and marked 20 approvals that Phase 2 then could not download (`DAILY_LIMIT_REACHED`), losing them.
R26. **The screener is told the source** (`--source reed`, screening 58): a Reed card with none of the Reed-only snippet fields is no longer logged as Caterer in the calibration data.
R27. **Launcher inside a container/microVM (hermes-fit 79/82/83/84/85, security-pii 70).** `ensure-chrome-cdp.js` no longer passes the inherited `TMPDIR` to `xvfb-run` and Chromium: it uses its own `state/rt/` (or `/tmp/rab-<hash>/rt` when the singleton socket path would not fit), because `xvfb-run` exits 1 when `TMPDIR` is missing or read-only and Chromium aborts with SIGTRAP when `TMPDIR + 46` exceeds 107 characters (both measured). It also sets `TZ=Europe/London` and `LANGUAGE=en_GB:en`, replaces an unusable `HOME` with `state/`, takes the container-dependent flags from `REED_CHROME_ARGS` (default `--no-sandbox,--disable-dev-shm-usage,--lang=en-GB`, replaced as a whole), finds Chromium through `CHROMIUM_PATH`, `/usr/bin/chromium*`, the Hermes image's `/etc/hermes/agent-browser-executable-path`, then `google-chrome*`, and prints which one (`CDP_LAUNCHING: starting Chromium (<source>) ...`). A failed start names its likely cause (`xauth` missing, `xvfb-run` cannot create its auth directory, Xvfb cannot start, sandbox unavailable, shared memory, singleton socket / profile in use, SIGTRAP abort) taken from the log of THAT launch. After every stop the launcher removes `.org.chromium.*` and `xvfb-run.*` from `state/rt` and the profile's `History`; cookies, local state and the session are kept. `--status` prints the chosen binary and the singleton budget. `--disable-gpu` is deliberately NOT a default (see browser-caterer.md deviation 18); `tests/reed/real-chromium.test.js` no longer adds it to its Chromium wrapper, so the acceptance test runs the production flag set. `--no-sandbox` and the fixed unauthenticated CDP port on 127.0.0.1 stay (accepted risk, docs/SECURITY.md); `REED_CDP_PORT` changes the port.
R28. **Files.** `reed-approved-queue-*`, `reed-empty-*` and `merged-queue-*` (names, current roles) are written 0600; Reed CV files (`cv-reed-<id>.<ext>` and the anonymized `.anon<ext>`) are written with `fsx.writeFileAtomic(..., 0o600)` so a kill never leaves a truncated CV that `findExistingCv` would attach; the full-CV extension comes from the same list Phase 2 searches (`pdf docx doc rtf txt`, else the content type, else `.pdf`); the anonymized CV text parser skips a file over 5 MB (card data only). Tests: `cv-files.test.js`.

R29. **The request path no longer depends on one hypothesis (Update D, first-page failure 2026-09-30).** (a) The token is resolved in Node (this process's token while it has more than 15 s left, else the session file when valid and a JWT, else `getToken()`'s navigate-capture) and embedded with `JSON.stringify` in the SAME `Runtime.evaluate` that sends the request; nothing sets `window.__capturedReedToken` any more (a test forbids it), so a document replacement between two CDP calls cannot produce an empty bearer. `reed-download`'s forced refresh calls `invalidateToken()` instead of clearing the page variable. (b) A token that is not a JWT (three dot-separated base64url parts, at least 50 characters) is never sent: after a capture attempt the error is `REED_TOKEN_MISSING` (`err.code`; retriable inside the attempt loop; `reed-api-client` does not turn it into a direct fetch or a relogin). A re-capture that cannot finish (for example the page shows no token within the time box) does not throw a good token away: the request is sent again with the token this process still holds, else the saved session token when it is a valid JWT, and the real HTTP 400 stays the final error; `REED_TOKEN_MISSING` is raised only when no usable token exists at all. (c) Before a request the tab must be `readyState` complete, quiet for `REED_TAB_SETTLE_MS` (1500) since its last navigation and unchanged (same `performance.timeOrigin`) between two polls 150 ms apart, at most `REED_TAB_READY_WAIT_MS` (10000; 0 = off); a tab that is settled but not on the search page is not waited for and not navigated (the API answers 401 as before: the live-tab-rule test still passes). (d) HTTP 400 whose body names `RequiredHeaderMissing` or `50010`, a missing token and a page replaced during the request (an error raised before any HTTP status was read, such as `Execution context was destroyed`; the text of a server answer never decides a retry) are retried, 3 attempts in all, pauses `REED_RETRY_BACKOFF_MS` (1500) times the attempt number, all inside `REED_RETRY_CAP_MS` (45000); before the second attempt the tab is located again and the token is captured once more (`refreshToken({timeoutMs})`: the navigate-capture, time-boxed to what is left of the cap); the final error keeps the old text (`Reed API POST HTTP 400: ...`, `status` 400) and gains `attempts`. 401, 403, 429, 451 and every other status are NOT retried and keep their messages. After the retries `REED_NAV_DURING_REQUEST` and `REED_TOKEN_MISSING` are final in `reed-api-client` (`isFinalBrowserError`): neither becomes a direct fetch, which Cloudflare would answer 403 and which would be misread as a relogin. The attempt loop checks its cap before each pause, not during an attempt; the bound is stated in `docs/parity/reed-first-page.md` section 4. (e) Every failed attempt logs one line, `REED_REQUEST_FORENSIC attempt=N/3 status=<n|none> code=<api code|none|REED_TOKEN_MISSING|REED_NAV_DURING_REQUEST|BROWSER_ERROR> headers=<names> token=<yes|no> len=<bucket> path=<pathname> sinceNavMs=<ms> sinceTokenMs=<ms> navDuringRequest=<yes|no|unknown> readyState=<state>`: names and coarse numbers only (no value, no query, no body). The legacy log line `Token seeded from reed-session.json` is now `Token taken from reed-session.json`.

R30. **A failed Reed attempt is a failure, not an empty search.** `reed-phase1.js`: a first-page error that is not 401/403 (`REED_RELOGIN_NEEDED`) or 451 writes `REED_FIRST_PAGE_FAILED: <reason> attempts=<n> streak=<k>` (reason such as `HTTP 400 code 50010`), counts the streak (`runtime/reed-first-page-streak.json`), raises `reed-first-page-failed` (R32), puts the streak in the `detail` of `runtime/reed-status.json` (state stays `ok`: the login is fine; the three-key shape is unchanged) and exits 1 with no queue. A genuine `Total pool: 0 candidates` is still exit 0 with an empty queue and ends the streak. Three more cases (Update D finalizer): (1) the error `No locations found for ...` (Reed's location lookup returned nothing for the place, raised by `reed-search.js` before any search request) is an empty search, not a failure: `REED_LOCATION_NOT_FOUND`, exit 0, empty queue with `locationNotFound: true`, status `empty`, no streak, no alert, no retry, and the log does not carry the words "Could not fetch first page" (every other error, including any other HTTP 400, stays a failure so a systematic break is never taken for unsearchable places); (2) `REED_TOKEN_MISSING` on the first page is a login problem: auth-failed marker reason `token_missing`, `REED_AUTH_FAILED`, exit 1, and the normal auth hold, retries and alerts; (3) when the first page worked (a pool) but NONE of the search pages of step 2 could be fetched, the run is a failure too: the line `REED_FIRST_PAGE_FAILED: <reason> attempts=<n> streak=<k> (no search page could be fetched)`, `phase1Stats.failed` true, `failureReason`, `errors` at least 1, exit 0 with the (empty) queue, so Phase 2 records status `failed`. A failed page is counted in `errors` whenever it happens; some pages failing while others were scraped is NOT a failure. The streak ends at the first search page that is actually fetched in step 2 (or at a genuine empty pool), not at step 1. `run-pipeline.js` reads the marker (and, for any other non-zero exit that left no queue and no auth failure, the exit code) and writes the placeholder queue with `phase1Stats: {failed: true, failureKind: first_page|phase1_exit, failureReason, failedAt, errors: 1, authFailed: false}`; it no longer says "recorded both-source attempt" for a failure (that text remains only for a clean exit 0 without a queue). Phase 2 (`process-approved-queue.js`) writes `reedStatus` (`failed | auth_failed | halted | limit | ok | empty | not_run`) into the results file and `reedStats.status` (and `failed`, `failureReason`, `errors: 1` for a failure) into `reedStats`, hence into `run_results.reed_json`; the run-level `errors`, the Caterer stats and the pending-search handling are unchanged (the Caterer half completes and is a success). The dashboard plugin's `/runs` Reed breakdown adds `status`, `failed`, `failureReason` only when recorded, and the page shows "Reed failed" and "not searched: <reason>" instead of OK / pool 0. There is no separate `reed_status` column: the status lives in `reed_json` (no schema change, no change to `backfill-run-results.js`).

R31. **The lost Reed half is not forgotten: the territory rule.** `territory-utils.markReedHalf` (called by Phase 2 right after the territory upsert, never failing the run): the Caterer half is real, so `last_searched` and `next_run_date` are written as before; in addition `territory_searches.reed_pending_since` (nullable date, column added when missing) is set to today by status `failed` or `auth_failed` (the oldest date of an open episode is kept) and cleared by `ok` or `empty`; any other status leaves it. The FIRST `failed` of an episode also pulls `next_run_date` forward to the first day from tomorrow (UTC) with free daily capacity, when later: one automatic retry through `queue-due-territories.js`. A second failure keeps the normal cadence. A run on a territory that is NOT due yet (a one-off or catch-up search ahead of its slot) leaves its `next_run_date` where it was (`upsertTerritory`; before, it rolled the date on by a whole interval, which pushed the next regular sweep a full interval past its due date), except for a priority downgrade, which re-bases the cadence as before; the one-day retry still pulls the date earlier. A run that is halted (screening down) or stopped by the daily view limit neither sets nor clears the mark, so an open mark stays open through it. `auth_failed` keeps its own bounded pending-file retries (R20, `reedAuthRetries`). Tests: `first-page-phase2.test.js`. Release addition (R34): a `not_run` with `owed=true` (a Phase 2 that completes a queue CV screening HELD before its Reed step ran) opens the mark and pulls the one retry like `failed`.

R32. **Alert `reed-first-page-failed`** (WARN, once per episode through `alertOnce`; CRITICAL once when 5 Reed attempts in a row failed, a design default; `alertOnce` now lets a higher severity through an open episode once and stores the severity in `runtime/reed-alert-episodes.json`). The episode and the streak end at the next first page that works.

R33. **`tools/reed-catchup.js`** (dry run by default, counts and territory codes only) lists the territories whose latest finished run since `--since` (default 2026-09-30) had no successful Reed half: `failed`, `skipped`, `reed_off` (Caterer-only run of a territory that asks for Reed) and `empty_with_log_failure` (old row with pool 0 and errors 0 plus a first-page failure in `logs/phase1-console-*.log` for that title and place), plus territories with a Reed-pending mark and no run row. `--queue N` writes up to N pending searches `zz-reed-catchup-<ms>-<8 hex>.json` (sources both, priority low, sorted behind every other pending file), never one already queued, quarantined, running or run today, at most `--per-day` per UTC day (ledger `runtime/reed-catchup.json`), limited by the Reed daily budget (nothing once `reed_daily_usage` reaches its limit; 20 views reserved per file). Idempotent, also for two processes started together: the analysis, the plan and the ledger are read under the `pending-searches` lock (the slow log scan is done before taking it). `--queue` refuses with exit 3 and writes nothing while Reed is switched off (`RESOURCER_SOURCES`) or held after an auth failure, because the run would redo the Caterer half and skip Reed again; the dry run and the list are not refused. A territory with an open Reed-pending mark is listed even when its latest run was halted or hit the daily limit, and a log line for a place Reed could not look up is not evidence of a failure. Tests: `catchup.test.js`. Release addition: a territory whose run CV screening merely HELD (status file with `phase2Hold`, not complete, under 7 days old) is left out and counted as `held by CV screening`.

R34. **A held both-source queue does not lose its Reed half silently (release).** With `CV_SCREEN=on`, Phase 2 exit 2 (held) leaves `phase2Hold` in the status file. When the Reed step DID run, the recovery completes the queue on its merged queue (Update C), so nothing is lost. When it did NOT run (Reed held or off, no merged queue), the recovery completes the Caterer queue alone, the pending search is consumed and, before this rule, the run row said `not_run`, which marks nothing. `process-approved-queue.js` reads `phase2Hold` of the status file of the queue it is completing (`heldBefore`) and passes `owed` to `markReedHalf` when the Reed status is `not_run`: the territory becomes Reed-pending with the one automatic retry, `reed-catchup.js` lists it (`skipped`), and the dashboard row shows Reed `not_run` as before. Proven by `tests/release/hold-and-reed.test.js` (and a run that was never held, or with Reed off, marks nothing).

Legacy quirks kept on purpose: the `reedFetch` wrappers fall back to a direct fetch after ANY browser-proxy error that is not a relogin/`HTTP 4xx` (so a 5xx or a dead browser is retried directly, which Cloudflare then answers with 403, read as `REED_RELOGIN_NEEDED`, which stops paging; a test pins this); a failing search page other than relogin/451 is skipped after 2 s (not retried); page 1 is fetched twice; with `--cv-limit` the rest of the page is neither approved nor marked seen; `run-pipeline.js` exits 0 even when Phase 2 failed and still writes `phase2Status='done'`; an expired `reed_daily_usage.daily_limit` row created by `candidates-db.js` keeps its own (default 300) limit; the daily date key is the UTC date (shared with `territory-scheduler.js` and `queue-due-territories.js`).

## Human-assisted Reed login (the operator's procedure)

Automatic login from a datacenter IP is expected to meet Cloudflare Turnstile. Nothing loops: the pipeline raises one critical alert (`reed-human-login`) and Reed is skipped (Caterer keeps running) until a human has logged in once.

1. On the instance: `cd <RESOURCER_HOME> && node scripts/cdp-reed-full-login.js --human` (add `--clean` if a wrong-country session must be discarded first, `--wait-min N` to change the 30 minute wait). It starts the Reed browser, opens the Reed login page in it, takes `browser.lock` (pipeline runs skip Reed meanwhile) and prints the steps below.
2. From your own computer forward the browser port: `ssh -N -L 9222:127.0.0.1:9222 <user>@<instance-host>` (use the port printed by the command; `REED_CDP_PORT`).
3. In Chrome open `chrome://inspect/#devices`, click Configure, add `localhost:9222`, then Inspect the Reed login page and log in there (solve the check, password, 2FA).
4. The command detects the login (a tab of its own reaching the recruiter area; tabs that were already there do not count), navigates to the search page, captures the token, saves the session, clears the block, sends an info alert and exits 0 with `REED_LOGIN_OK`. The persistent profile keeps the login afterwards (see R7).

Whether Hermes gives the operator a way to reach a loopback port, and whether Cloudflare accepts the login from that path, cannot be tested offline (see unverified list).

## Requirements on other packages (also in the structured result)

## Open issues

- `RESOURCER_SOURCES=reed` is accepted by the gate, but phase 1 still scrapes Caterer for `--sources reed` and runs Phase 2 inline, so Reed-only sourcing does not exist upstream (legacy behaviour).
- Between the lock check and the browser launch a Caterer run could start (no atomic check-and-launch across packages); the window is a few seconds.
- A hold skips the Reed half of every territory processed during it (the scheduler brings the territory back at its next interval). If the owner prefers Reed to be retried later instead, Phase 2 would need a "Reed held" flag that keeps the pending file without counting a retry; not done because it would re-run the whole Caterer half for each held territory.
- `alertOnce` is not atomic across processes (two Reed children finishing in the same millisecond could both alert); the pipeline runs one Reed child at a time, so this is theoretical.
- (Closed in the review round, R28: the full-CV writer uses Phase 2's extension list.)
- A kill after the Reed queue file exists (see R24) strands the approved candidates; the fix needs `process-approved-queue.js` (Reed row upsert) and `recover-stranded-phase1.js` (merged queue).
- `process-approved-queue.js` does not read `phase1Stats.reed.screeningHalted` or `dailyLimitReached`: a Reed half that could not run still consumes the territory (phase2-reed 18). One `incompleteRun` branch, like the Caterer one.
- `RESOURCER_SOURCES` excluding Reed only reaches `runtime/reed-status.json` through `run-pipeline.js` or `--sync-status` (Requirement 3a).
