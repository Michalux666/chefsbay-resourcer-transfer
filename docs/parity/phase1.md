## 2. Contract kept exactly

- Exit codes: 0 ok, 2 SESSION_STALE (credits path and browser-on-login path), 3 another pipeline active (run-lock exit 2 only), 4 TERRITORY_MISMATCH, 5 missing/invalid params (RESULTS_URL, JOB_TITLE, LOCATION, SOURCES), 6 BAD_URL_ENCODING, 7 params file unreadable or malformed; a `run-pipeline.js` exit code is passed through; a `process-approved-queue.js` exit code is ignored (legacy: always 0). New: 1 = fatal (see deviations).
- Order of checks: params file (7) -> mandatory params (5) -> SOURCES (5) -> URL normalisation -> encoding (6) -> territory (4) -> banner -> bridges -> lock (3) -> session (2) -> status file.
- Status file `runs/phase1-<yyyy-MM-dd-HHmmss>.json`, same 14 keys in the same order, `status` values `phase1_running` / `phase1_complete`, `pool = skippedDb + approved + skippedReview`, `phase2Status` null until the hand-off sets `pending`, the deferred rewrite carries `page: 0` (legacy quirk kept), UTF-8 no BOM, atomic.
- Queue file `downloads/approved-queue-<same suffix>.json`: same top-level keys and order, `phase1Stats` with the same 15 keys, `phase2Status` always `pending`, `creditsRemaining` is a digit string or `unknown`, `approved` in the stats is the pre-Zoho-filter count, candidate objects have the same 15 fields (phone whitespace removed, `currentEmployer` empty).
- Per-page checkpoint of the approved queue (only when non-empty) with the legacy shape `{searchDate, jobTitle, location, source:'caterer', candidates}`; recovery reloads a queue file that carries this run's suffix.
- URL: hash stripped, `PageNumber` removed, `SearchFormType=Targeted`, `SearchOptionColumn=ExactMatch`, `PageSize=50` injected when missing, all matched case-insensitively (PowerShell `-match`/`-replace` semantics); `%26` in a value -> 6; `CurrentLocation` compared case-insensitively with LOCATION (PowerShell `-ne` semantics), `+` is not decoded.
- Browser call forms: only `open`, `wait --load networkidle`, `eval -b`, `get url`, `state save` through `lib/browser`; per-call timeouts 90 / 90 / 60 / 20 / 60 s and 30 s for the probe; open or eval timeout skips the page and counts an error; networkidle timeout sleeps then evals; a non-timeout `open` failure is tolerated (the page is evaluated anyway).
- Eval decoding: one layer of JSON string unwrapping, `^(Error|Timeout|Exception)` (case-insensitive) rejects, `null` means zero cards.
- Silent-zero guard: page 1 (first successfully parsed page) with 0 cards is an error unless the page states an explicit zero; any later zero page is plain exhaustion.
- Repeated payload guard (3 repeats), MAX_PAGES stop, CV_LIMIT+5 stop (checkpoint still written), "short pages are not exhaustion".
- Counters are ported with their quirks: a retried page increments `pagesScraped`, `totalCandidatesSeen`, `skippedDb` and the round-trip count again; `browserRoundtrips` starts at 1; `pageTimings` is appended at exactly the legacy points (not on skipped pages, not on repeated-payload or zero-card stops).
- PASS 1: one `check-batch-scoped <ids> <JOB_TITLE>` per page, per-card `check` fallback on failure or unparseable output.
- PASS 2: reviewer called with `--mode batch --job --location --distance`, 20 s heartbeat lines (`HEARTBEAT: AI batch start/in progress/end`), the first line matching `^\[\s*[{\]]` is the result, `SCREENING_MODEL:` last marker wins, reject bookkeeping `add` if `unlockedPrev` else `seen`, then `reject-title`. Changed (deviation 22): a missing id or a `sys_invalid_result` answer is not rejected and not recorded.
- 3-strike rule: exit 3 (or API_UNAVAILABLE text when no exit code) counts a failure, the failure counter resets only on a parsed success, pause `SCREEN_PAGE_RETRY_PAUSE_SEC` (120 s) and retry the same page (re-navigated), third failure prints `STOPPING Phase 1: ...`, raises the halt (`AI screening unavailable`, blockedRun), `errors++`, alert, stops the loop; exit code stays 0. Changed by the integration rehearsal (docs/parity/integration.md, finding F1): when the halt was raised the run is marked `incomplete: screening-unavailable`; with nothing approved the hand-off is skipped (`PHASE2_SKIPPED`, status `phase1_abandoned`) so the territory and its pending search survive, with approved candidates Phase 2 still pushes them but keeps the territory and the pending search.
- Reviewer failure (no JSON, unparseable, exit other than 0/3 - changed by deviation 21): `FATAL AI review parse error ...`, `CAUSE:` line depends on `API_UNAVAILABLE|OAuth|Gateway HTTP 5`, `errors++`, stop. The run is now incomplete (`screening-error`) and the pipeline halt is raised for the API-text case.
- PASS 3: `add` for previously unlocked cards now happens after the unlock (deviation 23; legacy: before), missing token skips with an error, unlock JSON line detection (`^{` and `"success"`, shutdown assertion trailer cut), post-unlock title normalisation (postcode or empty title derived from the snippet head, then the search title, then a placeholder), single review fail-open (API unavailable, parse error, exit 1 all approve), clean reject -> `add`, no `reject-title`, not queued, `neverUnlocked` -> `add` after approval, 1.5 s pause, city order title city -> postcode map -> raw card city (> 2 chars), state from the city.
- Finalise: complete status, `Credits remaining` via `caterer-get-credits.js --update-db`, queue written twice (before and after the Zoho pre-check by `get-zoho-id`).
- Hand-off: zero approved + caterer-only -> inline Phase 2, exit 0, no session save; zero approved + both -> fall through; approved > 0 -> `PROGRESS_MESSAGE`, session save, `QUEUE_FILE`, `SCREENING_MODEL`, `CREDITS`; both -> `PHASE2_DEFERRED`, status rewrite, second session save, `run-pipeline.js --status-file <owned status file>`, exit code passed through; otherwise inline Phase 2 and `PHASE2_DONE`. `reed` alone behaves like caterer-only exactly as before.
- Console markers kept: `PHASE 1 START/DONE`, `Cards on page`, `SKIP (in DB)`, `APPROVED/REJECTED pre-unlock`, `UNLOCKED`, `QUEUED (n total)`, `[CHECKPOINT]`, `[RECOVERY]`, `HEARTBEAT:`, `WARN`, `STOPPING Phase 1`, `PIPELINE_BLOCKED`, `SESSION_STALE`, `PARAMS_FILE_*`, `SOURCES_*`, `TERRITORY_MISMATCH`, `BAD_URL_ENCODING`, `QUEUE_FILE:`, `CREDITS:`, `SCREENING_MODEL:`, `PHASE2_DEFERRED`, `PHASE2_DONE`, `PROGRESS_MESSAGE`. The legacy WhatsApp alert lines became `notify()` calls plus an `ALERT:` console line.
- Reliability layers of the legacy CLAUDE.md list: heartbeat around screening (5.3 / 3), per-call browser timeouts (4), networkidle settle sleep and silent-zero guard (5), `phase1_complete` handoff with the owned status file (8), ASCII-only source (9), Phase 2 stale-file guard is Phase 2's own (7). Watcher polling instructions (6) and the WSL wrapper (4) are gone with the LLM watcher and WSL.

## 3. Deliberate deviations

Section 7/8 of DESIGN.md and the brief:

1. **Empty-result probe fixed.** The legacy source lost its backslashes on 2026-09-04 (`0s+candidates`), so the explicit-zero branch never matched. The probe is now a `String.raw` template (`extract.js: EMPTY_PROBE_JS`) evaluated in the page, tested against a fake document and end to end. Two refinements: a leading boundary so "150 candidates" or "1,000 candidates" can never read as a zero, and the result must be an exact `EMPTY` line (the legacy substring match would also accept the word "empty" inside an error message).
2. Reed handling in the hand-off is unchanged; D4 (Reed no-burn) belongs to WP7.
3. No `review-tmp-*` files (DESIGN 7). Candidates reach the reviewer on stdin (`--candidates-file -`, supported by the real `ai-review.js`); `SCREEN_INPUT_MODE=file` writes a 0600 file under `runtime/screening-input/`, passes `--consume-input`, removes it on every exit path and sweeps leftovers older than an hour at startup. The unlock token (`candidateDataValue`) is never sent to the reviewer.
4. Reviewer flags added: `--source caterer --run-id phase1-<ts>` and (review-fix pass) `--with-codes` on every batch call, and on single reviews `--single-file -` with `{title, snippet, name}` on stdin (the card first name lets the reviewer's redaction work; the older `--name` / `--title` / `--snippet` flags still exist in the reviewer). Unknown flags are ignored by the legacy parser, the real one accepts them.
5. Real exit codes are used (the legacy host could not read them); the heartbeat end line shows the real code; there is no 20 s polling floor.
6. Timeouts for every child (DESIGN 9): run-lock 30 s, credits 180 s, DB 60 s, unlock 180 s, batch review 1500 s, single review 330 s, hand-off 3900 s, auto re-login 600 s. A batch timeout counts as "screening unavailable" (3-strike rule), a single-review timeout approves (fail-open), a hand-off timeout exits 1, an unlock timeout is an unlock parse error.
7. Halt raised with `lib/pipeline-halt.setHalt` instead of the CLI; the remedy text no longer names the legacy gateway; the alert text no longer claims "pending file kept" (Phase 2, not phase 1, decides that).
8. Console PII minimisation (DESIGN principle 3): postcodes are printed as outward codes, the `UNLOCKED:` line prints the id and a masked email, the card list prints the id, the outward code and the unlock flags (no names at all: the rehearsal found full names in the console log, finding F5), snippets are never printed except the first 200 characters of an unparseable eval, child output that is echoed goes through `env.redact`.
9. Queue and checkpoint files are written with mode 0600 (they hold names, emails, phone numbers); the status file stays 0644.
10. Checkpoint `searchDate` is the London date (legacy wrote `null` because `$searchDate` was never assigned). The first status write carries `skippedDb: 0, errors: 0` (legacy `null`, only because the variables were not yet initialised).
11. Params: a missing params file exits 7 (legacy ignored a non-existent file and carried on); unknown flags and non-integer values exit 5; JSON `null` for an integer is ignored (legacy cast it to 0); keys are matched case-insensitively and `-`/`_` tolerant; `SOURCES` is trimmed and lower-cased (legacy compared case-insensitively but wrote the raw text).
12. URL: `?PageNumber=n&x=y` keeps a valid query (`?x=y`); percent-decoding of `CurrentLocation` never throws.
13. `scripts/extract-js.b64` missing or empty exits 1 before any side effect (legacy carried on with an empty script).
14. Run id: an unset `PHASE1_RUN_TIMESTAMP` never adopts another run's files; if the current second is taken the next free second is used (`NOTE run id collision`). Setting `PHASE1_RUN_TIMESTAMP` resumes that run and reloads its checkpoint (the legacy recovery only worked by accident of two starts in one second). Timestamps and banner clocks are Europe/London.
15. New stop guards: five consecutive failed pages stop the run (legacy could loop indefinitely on a dead browser; `PHASE1_MAX_CONSECUTIVE_PAGE_ERRORS`), and MAX_PAGES also applies after a skipped page. The five-failure stop no longer hands an empty queue to Phase 2 (deviation 26).
16. An unexpected exception inside the page loop is logged, counted as an error and the run finalises with what is already unlocked (the legacy host kept going after non-terminating errors); an exception elsewhere exits 1 with `FATAL`. A JSON object where an array of cards is expected is a parse failure (legacy would have processed it as one card).
17. Signals: SIGTERM, SIGINT and SIGHUP kill the children, remove any input file and mark a status that is still `phase1_running` as `phase1_abandoned` (so the global lock releases at once), then exit 143 / 130 / 129. A SIGKILL leaves the running status for cull-ghost, as before.
18. `Save-CatererSession` also refuses to save from the device-verification page (`SafeListLoginBlocked`), and creates the state directory.
19. Extra `WARN` lines where the legacy script was silent: failed DB bookkeeping writes, a run-lock that did not complete cleanly (still treated as "clear"), a non-timeout `open` failure, a failed session save.
20. The bridge is removed only if its resolved path differs from our own status file (legacy compared raw strings).

### Review-fix pass (deviations 21 to 34)

Made after eight adversarial reviews; every item has a regression test that fails against the pre-fix code (`tests/phase1/e2e.incomplete.test.js`, `e2e.realdb.test.js`, `unit.params-url.test.js`, `e2e.exitcodes.test.js`).

21. **Every early stop caused by the reviewer keeps the territory** (finding "Reviewer failures other than exit 3 still burn the territory", reproduced: reviewer exit 1 ended in Phase 2 with 0 candidates, `Territory DB updated ... next: +7 days`, pending file deleted). `screen.js: reviewerFailure` marks the run incomplete `screening-error` for: no JSON, unparseable JSON, exit code other than 0/3 even when JSON was printed, `[]` for a non-empty page, and a page of two or more where every result is unusable. The mark is independent of whether the halt could be written (the 3-strike exit-3 path too: `screening-unavailable`). When the reviewer text matches `API_UNAVAILABLE|OAuth|Gateway HTTP 5` the pipeline halt is raised (reason `AI screening unavailable`) and the `phase1-screening-auth` critical alert fires; that case is never given up, the halt governs the re-runs. A non-API fault is counted per search in `runtime/phase1-incomplete-runs.json` (key `title|location|distance`, forgotten after 24 h, status fields `incompleteRuns` / `incompleteLimit`): after `PHASE1_INCOMPLETE_MAX_RUNS` (3) runs in a row that ended early the next run completes normally (the territory is consumed once, `incompleteGaveUp` in the status file, critical alert `phase1-incomplete-giveup`), so a deterministic fault cannot re-run every minute for ever. The counter lives outside the pending file on purpose (supervision owns that file and its quarantine); it is cleared by any run that finishes without stopping early. If a halt cannot be written the hold is bounded the same way.
22. **A system-invalid or missing reviewer result is not a verdict** (findings "System-invalid screening results are recorded as real rejections", "Small pages ..."). Phase 1 passes `--with-codes`; a candidate whose result is missing or `sys_invalid_result` gets `NOT DECIDED`, is neither rejected nor recorded (no `seen`, `add` or `reject-title`) and counts as an error, so it is screened again. The engine side (4xx from both models, all-invalid calls, cross-call streak) is in docs/parity/screening.md item 17.
23. **`add` is written after the unlock, for every queued candidate** (findings "unlockedPrev cards are marked unlocked before the unlock", "Queued card with neither flag is never recorded"). A failed, timed-out or unparseable unlock leaves an approved `unlockedPrev` candidate unrecorded so it is screened again; a card with neither flag is recorded once queued. The checkpoint still comes first (finding F3). A candidate already in the queue (resume, duplicate checkpoint entry) is not unlocked or queued twice; `loadCheckpoint` drops duplicate ids.
24. **A broken database stops the run** (finding "Dead, locked or read-only candidates.db is not detected"). `candidates-db.js check` exits 2 on error (docs/parity/core.md D15); `dedupe.js` treats only `exit 1` with the `NEW: <id>` line as new and stops the page on anything else (`FATAL candidates.db check failed`), before any screening or unlock. Three bookkeeping writes in a row failing (`PHASE1_DB_FAIL_LIMIT`) mark the database broken and stop the run. Both end as incomplete `db-unavailable`, critical alert `phase1-db-unavailable`, never counted or given up (Phase 2 needs the database too). Unverified: how the supervision fitness gate treats the same faults (its owner).
25. **Bridge flip keeps `updatedAt`** (findings on the exit-3 quirk). A leftover `phase1_initializing` file that `run-lock` already ignores no longer blocks the run that cleared it; a fresh one (a live spawn) still blocks for the rest of the 5-minute taking-over life.
26. **A run that scraped nothing keeps the territory** (findings on the 5-consecutive-failure stop, the silent-zero abort, page-1 failure). Five consecutive failed pages, the silent-zero abort, an unexpected exception in the page loop, and any run with no scraped page and at least one error end as incomplete `scrape-failure` / `run-error`, bounded exactly like item 21 (a permanently failing territory is consumed on the third run). A genuinely empty remote territory (explicit "0 candidates") is still consumed at once. With `--sources both` an incomplete Caterer stop with nothing approved also skips the Reed hand-off for that run: the territory is retried as a whole. Acceptance check: capture the real page text of a genuinely empty territory (LL23, ZE1) so the probe recognises it; until then a remote territory that the probe misreads is held three times and then consumed with a critical alert instead of being consumed silently. Empty or whitespace eval output is read as zero cards again (legacy `ConvertFrom-Json` behaviour), so it reaches the probe on page 1 and is plain exhaustion after that.
27. **Unlock circuit breaker** (finding "A blocked unlock endpoint burns the territory silently"). `PHASE1_UNLOCK_FAIL_LIMIT` (5) consecutive unlock failures (a candidate without a token does not count; a success resets) stop the run as incomplete `unlock-failing` with a `phase1-unlock-failing` warning; bounded like item 21.
28. **Status file keeps moving**: `updatedAt` is refreshed by the screening heartbeat and before every candidate of the unlock loop (finding "Status updatedAt is not refreshed inside a page ... ghost-culled and recovered concurrently"). `finalise` sets `phase2Status: pending` before the first `phase1_complete` write, so a kill between that write and the hand-off stays recoverable (the file that Phase 2 later turns into `complete` is unchanged).
29. **Session**: the device-verification page (`SafeListLoginBlocked`) counts as a logged-out browser in `validateSession` (exit 2 after the one re-login), like `saveCatererSession` already did. An `about:blank` URL is still accepted (a cold daemon after a state load may report it; UNVERIFIED-LIVE, the silent-zero guard and item 26 now cover a run that then scrapes nothing).
30. **`RESULTS_URL` must be https on `caterer.com`** (exit 5, `BAD_RESULTS_URL`), so the signed-in browser is never pointed elsewhere. `BAD_URL_ENCODING` (6) now fires only when an encoded `&` swallows the next parameter (`CW4%26SearchString=`); a legitimate `%26` in a title (`Food+%26+Beverage`) is fine.
31. **Privacy**: a parse failure of card JSON logs the kind and position of the failure and, for card-like JSON, only its length; an unparseable unlock output that looks like a candidate (name, email, phone keys) is logged by length only; the single review sends snippet, title and first name on stdin (`ai-review.js --single-file -`), never on the command line.
32. New environment settings: `PHASE1_INCOMPLETE_MAX_RUNS` (3), `PHASE1_UNLOCK_FAIL_LIMIT` (5), `PHASE1_DB_FAIL_LIMIT` (3). New files: `runtime/phase1-incomplete-runs.json`. New status/queue fields: `incompleteRuns`, `incompleteLimit`, `incompleteGaveUp` (status), `incomplete` values `screening-error`, `scrape-failure`, `unlock-failing`, `db-unavailable`, `run-error` (Phase 2 only checks that the field is set). New alert keys: `phase1-incomplete-giveup` (critical), `phase1-db-unavailable` (critical), `phase1-unlock-failing` (warn).
33. Not changed on purpose: the empty-result probe patterns (a "0 candidates" placeholder in the results shell could read as a genuine zero; needs the live page text, acceptance item), non-Caterer coverage of `about:blank`, `unlockOne` token on the command line (the unlock script is another package's), and `Boolean(approved)` (the real reviewer returns strict booleans).
34. Test infrastructure: `tests/phase1/harness.js` also copies `lib/browser-env.js` when the real browser library is used (the browser package split it out of `browser.js`); the fake reviewer and database learned `--with-codes`, `--single-file`, exit-2 checks and write failures.

## 4. Known legacy quirks kept on purpose

- `Boolean(approved)`: a reviewer answering the string `"false"` would approve (the real reviewer returns strict booleans, D2).
- Reed-only (`--sources reed`) still scrapes Caterer and runs Phase 2 inline.
- (Fixed in the review-fix pass, deviation 24.) The pre-check for a dead DB used to count a failing `check` as "new". A broken database now stops the run.
- (Fixed in the review-fix pass, deviation 25.) The bridge step used to refresh `updatedAt` of a foreign `phase1_initializing` file when flipping it to `phase1_taking_over`, so `run-lock` treated a leftover as active for 5 more minutes and the run that flipped it exited 3 (a likely cause of the 113 exit-3 runs in September 2026). The original `updatedAt` is kept now.
- (Fixed in the integration pass, finding F1: the run that discovers a screening outage used to consume its territory through the inline Phase 2. It no longer does; see section 2, the 3-strike rule. Fixed again in the review-fix pass, deviation 21, for every other reviewer failure.)
- Each unlocked candidate is written to the queue checkpoint right after it is queued and BEFORE the database marks it unlocked (finding F3): a kill in between costs a repeat unlock, never a candidate no run would push.

## 9. Open issues and requests to other packages

- **Reed gating (`RESOURCER_SOURCES`) is not applied in phase 1 on purpose.** If phase 1 downgraded `both` to `caterer`, Phase 2's safety net (`process-approved-queue.js`, "pending requested Reed/both but result is caterer-only") would keep the pending file forever and re-run the territory. The gate must be applied where the pending file or the params are created (queue-due-territories / watchdog `buildParams`), so pending file, params, queue file and status agree.
- **Retention sweep** should also remove orphans that this package can leave after a hard kill: `runtime/screening-input/*` older than 1 hour (only used with `SCREEN_INPUT_MODE=file`; phase 1 sweeps them itself at startup), `downloads/approved-queue-*.tmp` and `runs/phase1-*.tmp` (atomic-write temp names). `downloads/approved-queue-*.json` hold personal data (mode 0600) and follow the existing 3-day rule.
- **docs/ENV.md** needs the settings in section 6 (`DOCUMENTED_ENV` in `phase1/config.js` is greppable).
- **Bridge quirk and dead-DB fallback**: both fixed in the review-fix pass (deviations 24 and 25). The supervision owner should still treat `db-unavailable` and the other new `incomplete` values as "run ended early, pending search kept" (the runner already releases the claim on any `status.incomplete`), and may read `incompleteRuns` / `incompleteLimit` from the status file for its own quarantine; phase 1 gives a repeating fault up by itself after the limit.
- **Reed** (`reed-phase1.js`, another package): pass `--with-codes` and skip `seenReedCandidate` for `sys_invalid_result`, and pass `--source reed`; without them a Reed candidate whose answer was unusable is still marked seen for good.
- **`caterer-login.ensureLoggedIn`** must never call `process.exit` (it does not today): phase 1 calls it in-process, at most twice per run (credits path and browser-on-login path), each with a 600 s guard.
